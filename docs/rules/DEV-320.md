## Problem

A large PR is slow to review, hard to revert, and prone to stalling. The bigger
the change, the longer it sits and the more risk it carries into production.

## Solution

Keep each PR small. With an agent doing the coding, a small PR is cheap to
produce, cheap to review, and cheap to revert, so there is no reason to batch
behavior into one large diff. Features that once looked out of reach ship this
way, as a run of small steps.

1. Scope a PR to 3 to 15 minutes of your time, 6 minutes typical. That covers
   prompting, agent review, and fixes. The agent's own thinking time does not
   count against it.
1. Make one PR one `type(scope): action` title per [DEV-340](./DEV-340.md): one
   type, one scope, one thing the user can now do. If the title needs a second
   type or a second scope to be true, it is two PRs.
1. Split a feature by step: the data it reads, the calculation on that data, the
   output format, the command or screen that exposes it. Each PR carries its own
   tests and docs.
1. Do not open a PR for a config change or a small refactor alone. It rides with
   the step that needs it.
1. Treat more than about 400 changed lines, not counting tests and lockfiles, as
   a PR to split, whatever its title says.
1. Leave the default branch green and deployable after every PR. Code that
   nothing calls yet is fine. When a step cannot ship to production on its own,
   put it behind a feature flag.
1. Keep the PR moving. A PR with no activity for 24 hours is closed unless a
   comment explains the delay.

Good: a report ships as four PRs, `feat(hours)` for the calculation,
`feat(report)` for the format, `feat(commands)` for a command restriction, and
`feat(command)` for the command itself. Bad: one `feat(hours)` PR that carries
all four, or a `chore(config)` PR that changes one setting nothing uses yet.

### Acceptance Criteria

- [ ] The PR is scoped to 3 to 15 minutes of the author's time
- [ ] Its title has one type and one scope, and describes one user action
- [ ] It changes about 400 lines or fewer, not counting tests and lockfiles
- [ ] It carries its own tests and docs, and leaves the default branch
      deployable
- [ ] Any delay beyond 24 hours is explained in a comment
