## Problem

Small PRs that build on each other, opened one by one against the default
branch, cannot be read in order, wait on each other to merge, and lose the line
from the Spec to the shipped behavior.

## Solution

When a Solution takes more than one PR, ship the PRs as a stack with
[`gh stack`](https://github.com/github/gh-stack): each branch is based on the
one it depends on, and GitHub shows them as one stack.

1. Start the stack from the Spec PR when the Goal has one, then add the code PRs
   in the order they build on each other.
1. Create and update the stack with `gh stack` (`init`, `add`, `submit`,
   `sync`), not by retargeting branches by hand.
1. In each PR description, say what it is stacked on and what it adds, so a
   reader follows the stack bottom to top. A PR that nothing calls yet says so.
1. Merge with `gh stack merge`, which merges every PR up to the one you choose
   in a single step, bottom first. Merging one PR at a time from the GitHub page
   forces a rebase of every PR above it: the squash merge writes a new commit,
   and the branches above still carry the original ones.

Good: "Stacked on the calculation PR. Turns logged hours into the markdown the
command will post; nothing calls it yet." Bad: five PRs opened against the
default branch, each with a description that assumes the reader has read the
other four.

### Acceptance Criteria

- [ ] PRs that depend on each other are one `gh stack`, not separate PRs against
      the default branch
- [ ] The Spec PR, when there is one, sits at the bottom of the stack
- [ ] Each PR description says what it is stacked on and what it adds
- [ ] The stack merges bottom first, with `gh stack merge`
